## 시작: 내가 알던 도커

컨테이너 하나 띄워서 환경 분리해 뭘 써본다. 헤드리스면 X 서버가 없어서 어쩌고. 내 도커 지식은 딱 이 정도였다. 매일 6종 VIO 알고리즘을 컨테이너로 돌리면서도 그 밑에서 뭐가 일어나는지는 흐릿했다. 이번에 우리가 실제로 쓰는 실행 명령어 한 줄을 바닥까지 뜯어보기로 했다.

우리 OpenVINS 실행 스크립트의 핵심은 이거다.

```bash
docker run --rm -d --name ofm_openvins_... \
  --network=host \
  --ipc=host \
  -e ROS_DOMAIN_ID=7 \
  -v "$RUN_DIR:/run_dir" \
  vio/openvins-ofm:latest \
  bash -lc "... ros2 launch ..."
```

이 한 줄을 이해하려면 먼저 '컨테이너가 뭐냐'부터 다시 잡아야 했다.

## 뿌리: 컨테이너는 VM이 아니라 프로세스다

내가 컨테이너를 오해한 지점이 여기였다.

> **내 진단** 나는 컨테이너를 VM처럼 '완전히 차단된 다른 공간'으로 느끼고 있었다. 그런데 도커가 호스트랑 커널을 공유한다는 말에 그 느낌이 자꾸 흐려졌다. 벽으로 막힌 방 같은데 왜 발전기는 같이 쓴다는 거지? 이 찜찜함이 오해의 핵심이었다.

컨테이너를 이해하는 축은 이 한 문장이다. **컨테이너 = 호스트 커널을 그대로 공유하는 격리된 리눅스 프로세스 하나.** VM과의 결정적 차이가 여기서 갈린다. VM은 게스트 OS 커널을 따로 부팅한다. 그래서 무겁고 느리다. 컨테이너는 자기 커널이 없다. 호스트 커널을 빌려 쓴다.

증거는 커널 버전을 찍어보면 나온다.

```
호스트   uname -r : 6.8.0-124-generic
컨테이너 uname -r : 6.8.0-124-generic
```

VM이면 게스트 커널이 따로 떠서 달라야 하는데 같다. 부팅할 커널이 없으니 컨테이너 시작은 그냥 프로세스 하나 exec하는 속도, 밀리초다.

한 발 더 들어가면 '컨테이너는 그냥 호스트 프로세스'라는 게 눈에 보인다. 지금 도는 컨테이너의 메인 프로세스가 호스트에서 몇 번 PID인지 물어봤다.

```
docker inspect -f '{{.State.Pid}}' <컨테이너>  →  495560
ps -o pid,cmd --pid 495560                       →  495560  sleep infinity
```

컨테이너의 심장이 호스트 프로세스 테이블에 `495560 sleep infinity`로 그냥 들어 있다. 도커는 이 프로세스에게 커널을 시켜 '네가 보는 세상'을 몇 가지 가려줄 뿐이었다. VM이라는 착각이 풀렸다. VM은 건물을 통째로 따로 짓는 것이고, 컨테이너는 같은 건물, 같은 발전기(커널) 안에서 벽으로 방을 나눈 것이었다. 그 벽의 정체(namespace)는 다음 편에서 판다.

## 명령어 해부 1층: 생성, 수명, 식별

이제 명령어를 층별로 깐다. 커널 개념 없이 바로 이해되는 앞부분부터.

- **`docker run`**: 사실 두 동작이다. 이미지로부터 컨테이너를 `create`(만들고) + `start`(시작). `docker create` + `docker start`를 한 방에.
- **`--rm`**: 컨테이너가 끝나면 그 컨테이너를 자동 삭제. 여기엔 그 컨테이너의 쓰기 레이어까지 날아간다. 그래서 결과나 로그를 컨테이너 안에 두면 증발한다. 우리가 `-v`로 결과 폴더를 밖에 붙여 빼내는 이유가 이것이다. 이게 휘발성(ephemeral) 컨테이너다.
- **`-d` (--detach)**: 백그라운드로 띄우고 터미널을 돌려준다. 안 붙이면 컨테이너 로그가 터미널을 붙잡는다(foreground).
- **`--name`**: 사람이 읽는 식별자. 안 주면 도커가 랜덤 이름(`nostalgic_turing` 같은)을 붙인다. 우리 스크립트는 유일 이름을 만들어 나중에 `docker stop`으로 정확히 집는다.

나머지 플래그는 커널 개념이 있어야 제대로 읽힌다. 지도만 그려두고 다음 편으로 넘긴다.

| 플래그 | 하는 일 | 필요한 개념 |
|--------|---------|-------------|
| `--network=host` | 네트워크 격리를 끔 | net namespace (2편) |
| `--ipc=host` | 공유메모리 격리를 끔 | IPC namespace (2편) |
| `-e ROS_DOMAIN_ID=7` | 환경변수 주입 | (그대로) |
| `-v host:container` | 호스트 폴더를 컨테이너에 붙임 | mount, 영속성 (3편) |
| `vio/openvins-ofm:latest` | 씌울 이미지 | overlayfs (3편) |

## 곁가지: persistent 컨테이너의 실물

위 스크립트는 `--rm -d`라 '한 번 쓰고 버리는' 휘발성인데, 정작 지금 도는 컨테이너를 보면 메인 프로세스가 `ros2 launch`가 아니라 `sleep infinity`였다. 진짜 작업인 ros2는 그 밑 자식으로 붙어 있었다.

이게 persistent 컨테이너 패턴이다. 컨테이너는 '메인 프로세스가 끝나면 죽는다'가 철칙이라, 진짜 할 일을 메인으로 걸면 그게 끝나는 순간 컨테이너가 사라져 안에 들어가 볼 수가 없다. 그래서 아무것도 안 하고 안 죽는 `sleep infinity`를 메인으로 걸어 컨테이너를 살려두고, 실제 작업은 그 안으로 밀어넣는다. 이 영속성 얘기는 3편에서 제대로 판다.

## 다음 편

여기까지가 뿌리(컨테이너 = 격리된 프로세스)와 명령어 1층이다. 다음 편에서 `--network=host`와 `--ipc=host`의 정체를 판다. '격리'가 커널에서 실제로 어떻게 구현되는지(namespace)와 자원을 얼마나 쓸지 조르는 cgroup이다.
